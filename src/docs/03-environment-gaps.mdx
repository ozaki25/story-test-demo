# 環境差と落とし穴

このリポジトリを組む過程で実際に踏んだものだけを載せています。
いずれも「実ブラウザでは通るが jsdom では落ちる」形で現れるため、
Portable Stories を採用するかどうかの判断に直結します。

確認したバージョン: storybook 10.5.7 / vitest 4.1.10 / @testing-library/user-event 14.6.3 / jsdom 30.0.1

## 1. jsdom では play の引数から userEvent が取れない

**症状**: Portable Stories で play 関数を再実行すると `userEvent.click is not a function`。

**原因**: Storybook は play の引数に `userEvent` を注入するとき、
`globalThis.window.navigator.clipboard` の存在を条件にしています。
jsdom 30 には `clipboard` がないため、注入がスキップされます。

**対策**: `src/test/setup.unit.ts` で `navigator.clipboard` を補っています。

Story 側で `storybook/test` の `userEvent` を import して回避することもできます。
その場合、import を書き忘れた Story は実ブラウザでは通り jsdom だけ落ちます。
このリポジトリでは環境差を setup ファイル 1 箇所で吸収し、
Story は play の引数から受け取る書き方に統一しています。

## 2. Portable Stories と素の user-event を同じファイルで混ぜると壊れる

**症状**: `TypeError: 'get ownerDocument' called on an object that is not a valid instance of Node.`

```
HTMLElement.get [as focus]  storybook/dist/csf/index.js
patchFocus                  @testing-library/user-event/.../patchFocus.js
setupDirect                 @testing-library/user-event/.../setup.js
```

**原因**: Storybook は `HTMLElement.prototype.focus` をゲッターに差し替えています。
そのゲッターは `this.ownerDocument` を参照するため、
user-event の `patchFocus` がプロトタイプ上のディスクリプタを読んだ瞬間に、
Node ではないオブジェクトで `ownerDocument` が呼ばれた状態になります。

**対策**: `userEvent` を `storybook/test` から import します。
Storybook 側で用意された同じインスタンスなので二重パッチが起きず、
実ブラウザ側の play 関数とも挙動が揃います。

Vitest はファイル単位で環境を分離するため、
Story を使わないファイル（`LoginForm.plain.test.tsx`）では
素の user-event がそのまま動きます。同じリポジトリ内に
動くファイルと動かないファイルが混在することになります。

## 3. run() と render() を併用すると二重にマウントされる

`composeStories` が返す Story の `run()` は描画と play の実行をまとめて行います。
`render()` を併用すると二重にマウントされ、
`screen`（document.body 全体が対象）のクエリが両方を拾って
「Found multiple elements」で落ちます。

`src/test/portable.ts` の `runStory` は、テストごとに独立したコンテナを渡し、
後始末までを引き受けることでこれを防いでいます。

## 4. Testing Library の自動クリーンアップは globals: true のときだけ

`globals: true` にしていない構成では、Testing Library は `afterEach` を自動登録しません。
明示的に `afterEach(cleanup)` を呼ばないと前のテストの DOM が残り、
やはり「Found multiple elements」で落ちます。

## 5. form に noValidate がないとブラウザ側だけ落ちる

`LoginForm` の `<form>` には `noValidate` を付けています。

付けないと、実ブラウザではブラウザ標準のバリデーションが submit を止めてしまい、
自前のエラー表示まで到達しません。jsdom では標準バリデーションが動かないため、
**jsdom では通るのに実ブラウザでは落ちる**という、上の 1〜4 とは逆向きの差になります。

同じ Story を両方の環境で走らせていると、この種の食い違いはその場で見つかります。

## 6. テストの収集条件を手法別サフィックスで絞ると、テストが黙って消える

**症状**: テストを書いたのに実行されない。しかも全体は緑のまま。

**原因**: Vitest の `include` を手法別のサフィックスで絞っていた。

```ts
// これをやってはいけない
include: ["src/**/*.{portable,plain}.test.{ts,tsx}"];
```

この状態で `Button.test.tsx` という名前のファイルを作ると、
中身が何であれ収集対象から外れます。エラーも警告も出ません。

実際に必ず失敗するテストを置いて確認しました。

```
npm run test:unit → Test Files 2 passed, Tests 14 passed
npm test          → Test Files 4 passed, Tests 27 passed
```

このリポジトリでは収集を `src/**/*.test.{ts,tsx}` で行い、
手法単位の実行はコマンド側で絞っています（`npm run test:portable`）。
この形なら、規約から外れた名前のファイルも収集され、中身が壊れていれば落ちます。

## 7. 方式A の jsdom 実行はリンタから見るとアサーションのないテストに見える

**症状**: `vitest(expect-expect): Test has no assertions`

Portable Stories で play 関数を再実行する書き方では、
検証が Story 側にあるためテストファイルに `expect` が現れません。
リンタからは空のテストに見えます。

```ts
test("S1 空のまま送信するとエラーが出る", async () => {
  await runStory(EmptySubmitShowsErrors);
});
```

**対策**: `runStory` をアサーション関数として認識させます（`.oxlintrc.json`）。

```json
{
  "files": ["**/*.portable.test.tsx"],
  "rules": {
    "vitest/expect-expect": ["error", { "assertFunctionNames": ["expect", "runStory"] }]
  }
}
```

ルールを全体で無効化すると、本当に空のテストも検出されなくなります。
ここでは対象ファイルと関数名を限定しています。

## 8. tags を共有定数から展開すると黙って無視される

**症状**: タグを付けたのにサイドバーの扱いが変わらない。
型エラーも実行時エラーも出ない。

原因は、タグを共有定数に切り出してスプレッドしていたことでした。

```tsx
// これは効かない
const interactionOnly = { tags: ["interaction", "!autodocs"] } satisfies Partial<Story>;

export const NoDoubleSubmit: Story = {
  ...interactionOnly,
  name: "T6 ...",
};
```

```tsx
// これは効く
export const NoDoubleSubmit: Story = {
  tags: ["interaction", "!autodocs"],
  name: "T6 ...",
};
```

Storybook のインデクサは Story ファイルを**静的に解析**して `tags` を読みます。
実行時の値ではないので、変数を経由すると解決できません。
そして解決できなかったことは通知されず、既定のタグのまま扱われます。

型エラーも出ずテストも通るので気付きにくいところです。
ビルド後の `storybook-static/index.json` で各エントリの `tags` を見ると確認できます。

```bash
node -e "const j=require('./storybook-static/index.json');
  Object.values(j.entries).forEach(e=>console.log(e.name, e.tags))"
```

スプレッドに戻して確認したときの出力です。`interaction` も `!autodocs` も残っていません。

```
T6 送信中に submit が再度発火... ["dev","test","manifest","autodocs","play-fn"]
```

`title` や `component` など、インデクサが読む他のフィールドでも同じことが起きます。
