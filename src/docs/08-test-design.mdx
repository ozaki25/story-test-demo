# テスト設計

どの手法で書くかの前に、**何を検証するか**を決める必要があります。
ここでは、思いつきでケースを並べるのをやめ、技法から機械的に導出しています。

## 使った技法

| 技法               | 対象                       | 導出したケース |
| ------------------ | -------------------------- | -------------- |
| 状態遷移テスト     | フォームの状態と遷移       | T1〜T6         |
| デシジョンテーブル | 入力値の妥当性の組み合わせ | D1〜D4         |
| 同値分割・境界値   | 個々の入力値               | V1〜V8         |
| 操作経路           | ポインタ / キーボード      | K1             |

## 状態遷移テスト

`LoginForm` を状態機械として書き出します。

```
idle ──[不正な入力で送信]──▶ error ──[修正して送信]──┐
  │                                                   │
  └──[妥当な入力で送信]──────────────────────────────▶ submitting
                                          ┌───────────┴───────────┐
                                    [解決]▼                  [棄却]▼
                                        idle                    error
```

遷移を数え上げると、検証すべきケースが機械的に決まります。

| ID  | 遷移                            | 検証内容                             |
| --- | ------------------------------- | ------------------------------------ |
| T1  | idle → error                    | 空送信で両方にエラーが出る           |
| T2  | error → submitting              | 修正して送信し直せる                 |
| T3  | idle → submitting               | 妥当な入力で送信され、操作不能になる |
| T4  | submitting → idle               | 成功して操作できる状態に戻る         |
| T5  | submitting → error              | 失敗してエラーが出る                 |
| T6  | submitting → submitting（自己） | 二重送信されない                     |

**この表を書いた時点で、実装の欠陥が 2 つ見つかりました。**

**T5**: `onSubmit` が失敗したときの処理がありませんでした。`try` / `finally` はあるのに
`catch` がなく、未処理の Promise 拒否になっていました。画面には何も出ず、
利用者は送信できたのか分からないまま放置されます。

**T6**: 送信中の多重送信を防いでいませんでした。ボタンは押下を止めますが、
入力欄で Enter を押すとボタンを経由せずにフォームが送信されます。
「ボタンを無効にしたから大丈夫」で済ませていた箇所です。

どちらも、遷移を数え上げなければ気付かないものでした。
**設計の段階でケースを洗い出す価値は、ここに出ます。**

## デシジョンテーブル

email と password の妥当性の組み合わせを埋めます。

| ID  | email | password | 期待                  |
| --- | ----- | -------- | --------------------- |
| D1  | 妥当  | 妥当     | 送信される            |
| D2  | 妥当  | 不正     | password にだけエラー |
| D3  | 不正  | 妥当     | email にだけエラー    |
| D4  | 不正  | 不正     | 両方にエラー          |

もともと D2 が欠けていました。「片側だけ不正」を email 側でしか見ておらず、
対称なケースがない状態でした。表を書けば埋まります。

## 同値分割・境界値分析

パスワードの下限は 8 文字です。**境界そのものを踏む値を必ず入れます。**

| ID  | 入力                 | 期待           |
| --- | -------------------- | -------------- |
| V1  | 0 文字               | 入力必須エラー |
| V2  | **7 文字**           | 文字数エラー   |
| V3  | **8 文字**           | エラーなし     |
| V4  | email 空             | 入力必須エラー |
| V5  | email 空白のみ       | 入力必須エラー |
| V6  | `@` なし             | 形式エラー     |
| V7  | ドメインにドットなし | 形式エラー     |
| V8  | ローカル部なし       | 形式エラー     |

「短い例」と「十分長い例」を 1 つずつ置くだけでは、`<` と `<=` の取り違えを検出できません。
V2 と V3 が対になっていることが重要です。

## 前提: 手法は「どれか 1 つ」を選ぶ

このリポジトリは、複数の手法を組み合わせて 1 つのスイートを作るためのものではありません。
**競合する手法のうちどれを採用するかを決める**ための材料です。
採用が決まれば、選ばれなかった実装はまるごと消えます。

そのため、競合する手法はそれぞれが**単独で全ケースを賄えるように**実装してあります。
ケースを手法どうしで分担すると、単独で採用できるかどうかが判断できなくなるためです。

収録物は、競合するものとしないものが混ざっています。ここを分けて考える必要があります。

|                                                       | 関係                                                                  |
| ----------------------------------------------------- | --------------------------------------------------------------------- |
| **① play 関数** と **対照群 素の Testing Library**    | **競合する**。テストの正をどこに置くかの選択。どちらか一方だけが残る  |
| **実ブラウザ実行** と **④ Portable Stories（jsdom）** | ①を選んだ場合の**下位の選択**。実行環境をどうするか                   |
| **② スモークテスト** と **③ a11y**                    | **競合しない**。ただし①を選ぶかどうかで守備範囲が大きく変わる（後述） |
| **V1〜V8**（純粋関数）                                | **競合しない**。描画を伴わないので方式の選択と独立                    |

V1〜V8 を `*.plain.test.tsx` の中に置いていないのはこのためです。
そこに置くと、①を採用して対照群を消したときに巻き添えで消えます。
`validateLoginForm.test.ts` として独立させてあります。

## ②と③の守備範囲は、方式の選択に連動する

見落としやすい点です。

**①を選ぶと**、状態ごとに Story が増えます。T1〜T6・D1〜D4・K1 で 11 個の Story ができ、
そのすべてに axe が実行されます。エラー表示中・送信中・失敗表示中といった
**異常系の状態も a11y の検査対象になります**。

**対照群を選ぶと**、Story は「初期表示」を残すだけになります。
テストは `*.test.tsx` に書かれ、Story は増えません。
結果として **axe が回るのは初期表示だけ**になり、
エラー表示中や送信中のアクセシビリティは誰も検査しない状態になります。

同じことがスモークテストにも言えます。②は「Story の数だけテストが増える」仕組みなので、
Story が増えない方式を選べば、②から得られるものもほとんどなくなります。

つまり②③は「どちらを選んでも足せる」ものですが、
**得られる量は①を選ぶかどうかで決まります**。方式の比較では、
テストコードの行数だけでなくこの副次的な差も勘定に入れる必要があります。

## 意図的に対象外にしたもの

- **視覚的な差分（VRT）**: レイアウト崩れや色の変化は検出できません
- **複数コンポーネントをまたぐ結合**: 画面遷移や状態共有は対象外です
- **性能**: 描画回数やレンダリングコストは測っていません

「何を守れていないか」を書いておかないと、テストが緑であることが
過剰な安心につながります。
