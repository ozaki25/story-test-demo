# 選択肢と比較

**どれか 1 つを採用する**前提で並べています。
組み合わせて使うための表ではありません。採用が決まれば、残りは消えます。

比較対象のケースは共通で、`LoginForm` の T1〜T6（状態遷移）・D1〜D4（デシジョンテーブル）・
K1（キーボード操作）の 11 件です。導出の根拠は「1. 何を検証するか」を参照。
競合する手法は、それぞれがこの 11 件を単独で賄うように実装してあります。

## 選択肢

```
方式A: テストの正を Story に置く（play 関数）
        └─ 実行環境の下位選択
             A-1: 実ブラウザのみ
             A-2: jsdom のみ（方式A の jsdom 実行）
             A-3: 両方

方式B: テストの正を通常のテストファイルに置く（Testing Library）
        └─ Storybook はカタログとしてだけ使う（play 関数を書かない）
```

## 記述量

同じ 11 ケースを実装したときの実行行数（コメントと空行を除く）です。

| 方式                      | ファイル                                       | 実行行数 |
| ------------------------- | ---------------------------------------------- | -------- |
| A（Story に書く）         | `LoginForm.stories.tsx`                        | 188      |
| A-2 / A-3 の追加分        | `LoginForm.portable.test.tsx` の play 再実行分 | 31       |
| B（テストファイルに書く） | `LoginForm.plain.test.tsx`                     | 119      |

この 31 行は方式A の 188 行に対する追加分で、単独では成立しません。
Story に書いた検証を jsdom でも走らせるための配線にあたります。

A の 188 行には Story の定義そのもの（args・状態の宣言）が含まれます。
この部分は Storybook のカタログとしても機能します。

## 実行時間

| project                 | 件数 | 時間    | 内訳                    |
| ----------------------- | ---- | ------- | ----------------------- |
| storybook（実ブラウザ） | 19   | 11.0 秒 | うちセットアップ 5.4 秒 |
| unit（jsdom）           | 51   | 5.3 秒  | うちセットアップ 1.6 秒 |

実ブラウザ側は起動コストが支配的です。件数に対しては緩やかにしか伸びません。

## カバレッジ

方式ごとに独立して計測した結果です（`npm run coverage:browser` などで再現できます）。

|            | A-1 実ブラウザ | A-2 jsdom | B テストファイル | 参考: V のみ |
| ---------- | -------------- | --------- | ---------------- | ------------ |
| テスト件数 | 19             | 23        | 16               | 12           |
| 実行時間   | 9.1 秒         | 3.8 秒    | 3.5 秒           | 1.6 秒       |
| 行         | **100%**       | **100%**  | **100%**         | 33%          |
| 分岐       | **100%**       | **100%**  | **100%**         | 31%          |
| 関数       | **100%**       | **100%**  | **100%**         | 11%          |

競合する 3 つは、単独でいずれも 100% に到達します。
同じケースを実装しているので、カバレッジには差が出ません。
方式間で違うのは次節の「検出力の差」に挙げた項目です。

「V のみ」は、描画を伴うテストをすべて消して純粋関数のテストだけを残した場合です。
関数カバレッジは 11% になります。

母数は実ブラウザが 41 行、jsdom が 39 行と揃っていません。
v8 の計測が環境によって変わるためで、比較は率で行っています。

## カバレッジで見つかったこと

**T6 は、当初アサーションが通っていたのに、検証したい分岐を一度も通っていませんでした。**

最初の T6 は「送信中に Enter を押しても二重送信されない」と書いていました。
テストは緑でしたが、カバレッジでは二重送信ガードの `return` が未到達のままでした。

ガードを削除して実行したところ、**それでもテストは通りました**。
送信中は入力欄が `disabled` になるため Enter がフォームに届かず、
そもそも 2 回目の submit が発火していなかったのが原因です。
このテストは「二重送信を防いでいる」ではなく
「入力欄が無効だから届かない」を確認していただけでした。それは T3 が既に見ています。

ガードは「UI 以外の経路で submit が来ても二重送信しない」ための防御なので、
その水準に合わせて submit イベントを直接発火させる形に書き直しました。
書き直したあとは、ガードを削除するとテストが落ちます。

アサーションが通っていても、意図した分岐を通っているとは限りませんでした。
気付けたのはカバレッジに未到達行が残っていたからで、これは 3 方式のどれでも同じです。

## 検出力の差

|                            | 方式A（実ブラウザ）  | 方式A（jsdom のみ） | 方式B（jsdom）   |
| -------------------------- | -------------------- | ------------------- | ---------------- |
| T1〜T6・D1〜D4             | 検証できる           | 検証できる          | 検証できる       |
| K1（キーボード）           | **実際の挙動で検証** | 書けるが近似        | 書けるが近似     |
| ブラウザ標準バリデーション | 検出できる           | **検出できない**    | **検出できない** |
| a11y（axe）の対象          | **11 状態すべて**    | 11 状態すべて       | **初期表示のみ** |
| スモークテストの件数       | 11                   | 11                  | 1                |
| 状態がカタログに残る       | 残る                 | 残る                | 残らない         |

K1 は 3 つとも通ることを確認しています。
ただし jsdom で動いているのは user-event が実装したフォーカス処理であり、
ブラウザ自身のフォーカス順や Enter の扱いではありません。

**ブラウザ標準バリデーション**は実際に踏んだ差です。
`<form>` の `noValidate` を外すと、実ブラウザでは submit が止まり自前のエラー表示に
到達しませんが、jsdom では標準バリデーションが動かないため通ってしまいます
（「3. 環境差と落とし穴」参照）。jsdom だけの構成では、この差はテストをすり抜けます。

## 方式Bを選ぶと a11y の守備範囲が狭くなる

方式Aでは状態ごとに Story ができるので、エラー表示中・送信中・失敗表示中まで
axe の検査対象になります。方式Bでは Story が「初期表示」しか残らないので、
**異常系のアクセシビリティは誰も検査しません**。

スモークテストも同じで、Story が増えない方式では件数が 1 件になります。

方式Aで Story が増えても、サイドバーの表示は制御できます。
検証用の Story に `tags: ["!dev", "!autodocs"]` を付けるとカタログから外れ、
`test` タグは残るので axe もスモークテストも実行されます
（このリポジトリで実測し、非表示にしても実ブラウザ側は 19 件のままでした）。

## 判断の目安

**方式A（Story に書く）が向くケース**

- 状態のバリエーションが多く、見た目の確認にも価値がある
- a11y を継続的に見ていきたい
- デザイナーやレビュアーが Storybook を見る運用がある

**方式B（テストファイルに書く）が向くケース**

- Storybook を使っていない、または導入する予定がない
- 検証したいものが振る舞いだけで、状態を人が見る必要がない
- テストの書き方を既存の資産と揃えたい

**実行環境の選び方（方式Aを選んだ場合）**

- A-1（実ブラウザのみ）… 保証は最も強い。開発中のフィードバックは遅い
- A-2（jsdom のみ）… 速いが、ブラウザ固有の不具合を落とす
- A-3（両方）… 開発中は jsdom、CI は実ブラウザ。このリポジトリはこれを採っている

A-3 は二重に実行するぶん CI 時間が増えます。jsdom 実行の追加は 31 行です。
片方でしか再現しない問題は「3. 環境差と落とし穴」に 8 件挙げてあります。
