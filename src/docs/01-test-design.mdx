# 何を検証するか

どの手法で書くかの前に、**何を検証するか**が決まっている必要があります。
ケースは思いつきで並べたものではなく、技法から導出しました。

## 使った技法

| 技法               | 対象                       | 導出したケース |
| ------------------ | -------------------------- | -------------- |
| 状態遷移テスト     | フォームの状態と遷移       | T1〜T6         |
| デシジョンテーブル | 入力値の妥当性の組み合わせ | D1〜D4         |
| 同値分割・境界値   | 個々の入力値               | V1〜V8         |
| 操作経路           | ポインタ / キーボード      | K1             |

## 状態遷移テスト

`LoginForm` を状態機械として書き出します。

```
idle ──[不正な入力で送信]──▶ error ──[修正して送信]──┐
  │                                                   │
  └──[妥当な入力で送信]──────────────────────────────▶ submitting
                                          ┌───────────┴───────────┐
                                    [解決]▼                  [棄却]▼
                                        idle                    error
```

遷移を数え上げると、検証すべきケースが決まります。

| ID  | 遷移                            | 検証内容                             |
| --- | ------------------------------- | ------------------------------------ |
| T1  | idle → error                    | 空送信で両方にエラーが出る           |
| T2  | error → submitting              | 修正して送信し直せる                 |
| T3  | idle → submitting               | 妥当な入力で送信され、操作不能になる |
| T4  | submitting → idle               | 成功して操作できる状態に戻る         |
| T5  | submitting → error              | 失敗してエラーが出る                 |
| T6  | submitting → submitting（自己） | 二重送信されない                     |

T6 は当初「送信中に Enter を押す」と書いていましたが、
アサーションが通るのにガードの分岐を一度も通っていませんでした。
経緯は「2. 選択肢と比較」の「カバレッジで見つかったこと」を参照。

この表を書いた時点で、実装の欠陥が 2 件見つかりました。

**T5**: `onSubmit` が失敗したときの処理がありませんでした。`try` / `finally` はあるのに
`catch` がなく、未処理の Promise 拒否になっていました。画面には何も出ず、
利用者は送信できたのか分からないまま放置されます。

**T6**: 送信中の多重送信を防いでいませんでした。ボタンは押下を止めますが、
入力欄で Enter を押すとボタンを経由せずにフォームが送信されます。
「ボタンを無効にしたから大丈夫」で済ませていた箇所です。

## デシジョンテーブル

email と password の妥当性の組み合わせを埋めます。

| ID  | email | password | 期待                  |
| --- | ----- | -------- | --------------------- |
| D1  | 妥当  | 妥当     | 送信される            |
| D2  | 妥当  | 不正     | password にだけエラー |
| D3  | 不正  | 妥当     | email にだけエラー    |
| D4  | 不正  | 不正     | 両方にエラー          |

もともと D2 が欠けていました。「片側だけ不正」を email 側でしか見ておらず、
password 側の対称なケースがないままだったところに、表を埋めた時点で気付きました。

## 同値分割・境界値分析

パスワードの下限は 8 文字なので、境界そのものを踏む 7 文字と 8 文字を入れています。

| ID  | 入力                 | 期待           |
| --- | -------------------- | -------------- |
| V1  | 0 文字               | 入力必須エラー |
| V2  | **7 文字**           | 文字数エラー   |
| V3  | **8 文字**           | エラーなし     |
| V4  | email 空             | 入力必須エラー |
| V5  | email 空白のみ       | 入力必須エラー |
| V6  | `@` なし             | 形式エラー     |
| V7  | ドメインにドットなし | 形式エラー     |
| V8  | ローカル部なし       | 形式エラー     |

「短い例」と「十分長い例」を 1 つずつ置くだけでは、`<` と `<=` の取り違えは検出できません。
V2 と V3 のように境界の両側を踏んで、はじめて落ちます。

## ケースをどこに置くか

導出したケースのうち、描画を伴うもの（T1〜T6・D1〜D4・K1）は
方式A・方式Bのどちらでも実装できます。競合する方式なので、
このリポジトリでは両方に同じ内容を実装してあります。

描画を伴わない V1〜V8 は方式の選択と独立なので、
`validateLoginForm.test.ts` に分けてあります。
`*.plain.test.tsx` の中に置くと、方式Aを採用して方式Bを消したときに巻き添えで消えます。

## 意図的に対象外にしたもの

次の 4 つは対象外です。テストが全部通っても、ここは検証されていません。

- **視覚的な差分（VRT）**: レイアウト崩れや色の変化は検出できません
- **複数コンポーネントをまたぐ結合**: 画面遷移や状態共有は対象外です
- **性能**: 描画回数やレンダリングコストは測っていません
- **本格的なミューテーションテスト**: 手作業で 1 箇所ずつ確認しただけで、
  Stryker のような網羅的な仕組みは入れていません
