# 比較と使い分け

同じシナリオ S1〜S3 を各手法で実装した結果の比較です。

## 一覧

|                            | ① play 関数     | ② スモーク | ③ a11y       | ④ Portable Stories    | 対照群 素の TL     |
| -------------------------- | --------------- | ---------- | ------------ | --------------------- | ------------------ |
| 実行環境                   | 実ブラウザ      | 実ブラウザ | 実ブラウザ   | jsdom                 | jsdom              |
| テストを書く場所           | `*.stories.tsx` | 書かない   | `parameters` | `*.portable.test.tsx` | `*.plain.test.tsx` |
| Storybook にカタログが残る | 残る            | 残る       | 残る         | 残る（Story 側）      | 残らない           |
| 実ブラウザ固有の挙動       | 検証できる      | 検証できる | 検証できる   | 検証できない          | 検証できない       |
| 追加コスト                 | 中              | ほぼゼロ   | ほぼゼロ     | 小                    | 中                 |
| 速度                       | 遅い            | 遅い       | 遅い         | 速い                  | 速い               |

## 実測値

このリポジトリでの実行時間です。規模が小さいので絶対値ではなく比率を見てください。

| project                 | 件数 | 時間   | 内訳                    |
| ----------------------- | ---- | ------ | ----------------------- |
| storybook（実ブラウザ） | 13   | 6.0 秒 | うちセットアップ 4.1 秒 |
| unit（jsdom）           | 28   | 3.1 秒 | うちセットアップ 1.4 秒 |

実ブラウザ側は起動コストが支配的です（6.0 秒のうち 4.1 秒）。
件数に対しては緩やかに伸びるので、Story が増えても差がそのまま広がるわけではありません。
逆に言うと、テストが少ないうちは実ブラウザ側の遅さが目立ちます。

## 記述量の比較（シナリオ S3）

同じ「送信中はフォームが操作できない」を書いたときの違いです。

**① play 関数**: 送信中の状態を args として宣言し、Story として固定できます。

```tsx
export const SubmittingDisablesForm: Story = {
  args: { onSubmit: fn(() => new Promise<void>(() => {})) },
  play: async ({ canvas, userEvent, step }) => {
    /* 操作と検証 */
  },
};
```

**④ Portable Stories（使い方 A）**: 上の Story をそのまま再利用します。書くのは 1 行です。

```tsx
test("S3 送信中はフォームが操作できない", async () => {
  await runStory(SubmittingDisablesForm);
});
```

**対照群 素の TL**: 準備をテスト側に毎回書きます。

```tsx
const onSubmit = vi.fn(() => new Promise<void>(() => {}));
render(<LoginForm onSubmit={onSubmit} />);
// ... 操作と検証
```

記述量そのものは大きく変わりません。差が出るのは**準備の共有**と**成果物の再利用**です。
①で書いた args と play は、④でそのまま使い回せます。
対照群で書いたものは、そのテストの中だけで完結します。

## 使い分けの指針

**Story にする価値があるかで決める。**

Story にする価値とは「その状態を人が見て確認したいか」です。
エラー表示、送信中、権限による出し分けは見て確認したい状態なので Story にします。
バリデーション規則の網羅は見て確認したいものではないので、
関数として切り出して普通の単体テストを書きます
（`LoginForm.plain.test.tsx` の `validateLoginForm` のテストがその例）。

「何でも Story 経由にする」と、カタログとしての一覧性が落ちます。
Story が 100 個並んでいて、その 80 個がバリデーションの組み合わせだったら、
Storybook を開く意味が薄れます。

**実行環境は目的で選ぶ。**

- 開発中の高速なフィードバック → jsdom（④）
- マージ前の確からしさ → 実ブラウザ（①②③）

両方に同じ Story を流せるのが、Story を土台にすることの一番の利点です。
どちらか一方でしか再現しない問題（「5. 落とし穴」に挙げたもの）も早期に見つかります。

## 段階的な導入の順番

ゼロから入れるなら、コストの低い順に敷くのが現実的です。

1. **② スモークテスト** … Story を書くだけ。追加コストがほぼない
2. **③ a11y** … `parameters` の 1 行。既存の違反は `'todo'` で保留する
3. **① play 関数** … 重要な振る舞いから順に格上げする
4. **④ Portable Stories** … 実行時間が気になり始めたら、速いほうの経路を足す

④を最初に入れる必要はありません。①の Story が育ってから足すと、
その時点で既に再利用できる資産が揃っています。
